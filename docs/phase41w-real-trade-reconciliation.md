# Fase 41W: conciliación Real (trabajo en curso)

La rama contiene un primer importador de Activity Flex XML y una proyección privada de conciliación. **La fase aún no está terminada**: el comando de reconstrucción no incorpora evidencia verificable de inventario inicial ni de cobertura de todas las ejecuciones y eventos. Por esa razón mantiene `INCOMPLETE_HISTORY` y no genera resultados económicos como si estuvieran verificados. El motor FIFO se prueba por separado con inventario inicial sintético conocido; todavía no debe utilizarse como cálculo financiero de la cuenta Real.

## Fuente y configuración

IBKR permite crear y ejecutar consultas Flex de Activity con salida XML en Performance & Reports → Flex Queries. La sección [Trades de Activity Flex](https://www.ibkrguides.com/reportingreference/reportguide/tradesfq.htm) distingue ejecuciones, órdenes y lotes cerrados. Seleccione detalle `EXECUTION` y los campos de cuenta, IB Execution ID, Trade ID, conid del instrumento, underlyingSymbol, assetCategory, moneda, expiry, strike, putCall, multiplicador, fecha y hora, buySell, openCloseIndicator, transactionType, quantity, tradePrice, ibCommission, taxes, ibCommissionCurrency, fifoPnlRealized y levelOfDetail. El importador inicial solo admite el formato `FlexQueryResponse` Activity XML con una cuenta; no admite Trade Confirmation, archivos comprimidos, otros niveles de detalle ni múltiples cuentas. El operador informó que importó localmente un extracto auténtico; aún falta validar otras configuraciones y variantes de Flex.

Configure en `.env.local` la cuenta Real Primary mediante `TRADING_POC_REAL_ACCOUNT_ID` y declare `TRADING_POC_FLEX_TIMEZONE=America/New_York` únicamente si esa es la zona elegida para la consulta Flex. El importador acepta inicialmente solo identificadores con prefijo `U` seguido de dígitos; otros tipos de cuenta quedan fuera de este prototipo. La cuenta debe coincidir exactamente en el documento y en cada ejecución. La comprobación no autentica criptográficamente el archivo manual ni corrobora que el alias `Primary` de 41V corresponda a esa cuenta. El importador rechaza cuentas Paper `DU`, fechas inválidas y horas locales ambiguas en el cambio de horario. La zona declarada por el operador no se deduce del archivo.

En Windows coloque una copia del XML en la carpeta privada de importaciones configurada por Fase 41V. El CLI verifica la ruta física, limita el archivo a 5 MiB, no publica su contenido ni su ruta, y conserva hash y filas normalizadas en SQLite privada. El original queda bajo control del operador. El usuario informó una prueba privada con un extracto auténtico; ello no acredita compatibilidad con todos los formatos o configuraciones de Flex.

```powershell
npm.cmd run real-trades:reconcile -- file "$env:LOCALAPPDATA\Trading-POC\real-trades\imports\activity.xml" --confirm-real-primary
npm.cmd run real-trades:reconcile -- rebuild
```

El segundo comando genera una proyección identificada por hash. La misma entrada y el mismo código producen la misma proyección; una modificación no borra la anterior. Los endpoints locales protegidos por `x-local-token` usan `GET /api/v1/real-trades/reconciliation?view=summary|executions|episodes`, con `limit` hasta 100 y `offset`. Para una evidencia específica se usa `view=evidence&id=<hash>`; `snapshot=<hash>` permite consultar una versión anterior. La vista informa `PARTIAL` mientras la cobertura permanezca sin verificar y `STALE` si cambian las entradas o el código desde la proyección. Las consultas no reconstruyen automáticamente.

## Criterios y límites

La coincidencia utiliza exclusivamente el IB Execution ID exacto y comprueba los datos económicos y temporales presentes. Un mismo ID con versiones distintas queda ambiguo; una contradicción con 41V queda en conflicto. Los datos documentados en un XML manual sin autenticación se identifican como `DOCUMENTED_CONTRACT`, no como `VERIFIED_CONTRACT`. El conid de la opción se mantiene separado del subyacente; no se presupone multiplicador 100. Los símbolos OCC de 21 caracteres se contrastan con el parser existente sin usar su multiplicador predeterminado. Las ejecuciones sin coincidencia o con campos incompletos siguen pendientes.

El ID de orden es distinto del ID de ejecución. Cuando ambos documentos incluyen IDs de orden diferentes, `orderComparison=DIFFERENT` conserva la discrepancia para revisión: no se declara que los IDs sean equivalentes. La coincidencia contractual puede seguir documentada cuando el ID de ejecución y las demás comprobaciones estrictas coinciden, pero la diferencia de orden bloquea la atribución financiera. Si falta un ID de orden se informa `MISSING`; si coinciden se informa `MATCH`.

Para comisiones USD procedentes de la versión `AIRTABLE` de 41V se usa la convención comunicada por el operador: costo positivo y crédito negativo. Flex se interpreta como efecto monetario firmado: costo negativo y crédito positivo. Solo para compararlas se invierte el signo del valor Airtable; **no se alteran los datos almacenados ni se aplica valor absoluto a ambos importes**. Una comisión Airtable negativa frente a una comisión Flex negativa es una discrepancia de signo, no un costo coincidente. CSV y JSON no heredan esta convención automáticamente: quedan `UNKNOWN_SOURCE_CONVENTION`. Monedas incompatibles, no declaradas o distintas de USD quedan `UNKNOWN_CURRENCY`; una comisión ausente queda `MISSING`.

La comparación usa enteros decimales exactos, sin `number`. Si los importes normalizados son iguales se informa `EXACT`. Para Airtable, 41V pudo guardar un número JSON sin ceros finales; por ello se utiliza como hipótesis la precisión visible, con un mínimo de dos decimales y máximo de ocho. La tolerancia es media unidad del último decimal supuesto: como máximo USD 0.005 para una representación en centavos, y menor cuando se conservaron más decimales. Una diferencia no nula dentro de ese límite se informa `POSSIBLE_ROUNDING`, no como igualdad verificada; fuera del límite se registra `COMMISSION_MISMATCH` y el importe no se concilia. La tolerancia no demuestra que Airtable haya redondeado ni se aplica a precios, cantidades, contratos, fechas o IDs. `commissionComparison` expone fuente, importes originales, efecto normalizado, diferencia, precisión supuesta y tolerancia en la API local autenticada.

Las ejecuciones identificadas pueden formar grupos estructurales `CANDIDATE_GROUP` aunque existan otras sin identificar. Estos grupos no establecen que la posición estuviera inicialmente en cero ni que todas sus entradas y salidas estén presentes. Las ejecuciones no identificadas aún podrían corresponder al mismo contrato, por lo que mantienen bloqueada la atribución financiera; cantidades de posición y resultados quedan desconocidos cuando no existe evidencia suficiente. El cálculo económico sigue siendo independiente de la creación del grupo y `coverage` permanece `UNVERIFIED`.

El FIFO experimental separa episodios tras un cierre total y representa cantidades y resultados con fracciones exactas de enteros, sin redondear con `number`. El resultado bruto de las cantidades emparejadas es `(prima venta − prima compra) × multiplicador × cantidad`. Las comisiones e impuestos de cada fill se reparten proporcionalmente entre sus cantidades cerradas y se suman con su signo; si falta alguno o la comisión está en otra moneda, el neto queda desconocido. Otros costos no acreditados también impiden afirmar completitud económica. IBKR indica que el PnL realizado de Activity incluye comisiones en la base de costo. Por tanto, el PnL reportado se conserva aparte y no se declara comparable sin revisar los métodos de lotes y otros ajustes. El FIFO local es una convención, no prueba del método fiscal de IBKR.

Faltan todavía la ingesta y conciliación de lotes cerrados oficiales, eventos de ejercicio/asignación/vencimiento/transferencias, evidencia verificable de inventario inicial y cobertura, y las pruebas de todos los casos exigidos. No se interpreta la ausencia de eventos o de una compra como evidencia de que no existieron. `coverage=UNVERIFIED` no se convierte en completitud por importar un archivo sin errores. Para recuperar una importación, corrija el archivo o la configuración y vuelva a ejecutar el comando: un hash idéntico es idempotente y un archivo modificado se conserva como evidencia adicional, sin reemplazar la anterior.

Los archivos reales, la cuenta y la base SQLite deben permanecer privados. No hay órdenes ni conexión TWS Live en este módulo. Las pruebas automatizadas usan datos sintéticos; faltan una revisión integral de seguridad y el conjunto completo solicitado antes de proponer merge. Cada cambio debe superar la CI correspondiente.
